## 四、性能实测：推翻了「降采样率」这个前提

用户原本打算把 30 MHz 降到 1 MHz 甚至 500 kHz，理由是「CAF 乘法最吃算力」。

**实测把 30 MHz 单步拆开（60 万样本 × 2 通道）：**

| 步骤 | 耗时 | 占比 |
|---|---|---|
| sc16 → float 定标 | **7.98 ms** | **85.8%** |
| `conj(ch0)*ch1` 乘法 | 0.99 ms | 10.6% |
| 抽取 | 0.33 ms | 3.6% |
| 512 点 FFT | 0.01 ms | 0.1% |

→ **CAF 乘法只占 10.6%，瓶颈是格式转换。**
原因是 `recv[0]['re']` 是结构化 dtype 的字段视图，stride=4 字节却只读 2 字节，对 cache 极不友好。

**旧设计做不到实时的根因**：30MHz/DECIM=16/Tw=0.2 → `nperseg=375,000`，
单次 FFT 就要 **23.5 ms**（超 20ms 预算 118%），而 375k 个 bin 只用了 240 个（**0.064%**）。

**优化后（30 MHz 全带宽）**：朴素 11.66ms → 连续块转换+einsum 融合 **4.06ms** → 加 TDD 门控 **1.49ms**。

**核心思想**：TDD 每 1ms 才发一次 → 信息真实速率就是 1 kHz，数据速率是 10–30 MHz。
把每个 TDD 帧塌缩成**一个复数**不丢任何信息（物理决定，非近似），
整个加速就是尽早压掉这 10⁴ 倍差距。

**顺带回答的两个问题：**
- **不要用 GPU**：FFT 只要 0.01ms，元素级操作是 memory-bound，kernel 启动+PCIe(50–200µs) 和整个 CPU 计算同量级。
- **B210 的 FPGA 用不上**：B2xx 不支持 RFNoC（本机 RFNoC 镜像数=0）；
  官方 `.rpt` 显示 **DSP48A1 已用 152/180 = 84%**；Spartan-6 只能用 2013 年停产的 ISE 14.7。

## 五、阶段 1：实时多普勒（18:25–18:40）

### 真机结果（B210 **serial=32392D3**，注意不是旧代码里的 321D889）

| fs | 步数/时长 | p50 | p99 | 余量 | overflow | RSS |
|---|---|---|---|---|---|---|
| **10 MHz** | 3000 / 60s | **4.07 ms** | **5.86 ms** | **3×** | **0** | 60 MB（无泄漏）|
| 30 MHz | 1214 / 25s | 9.24 ms | 14.57 ms | 1× | 51 ⚠️ | 92 MB |

10 MHz 下 3000 步 / 60 秒 = **精确 50 步/秒**。
无泄漏（30s 涨 27.8 MB、60s 涨 27.3 MB，完全一致）。
30 MHz = 240 MB/s 接近 B210 USB3 上限，不推荐。

### 修掉的 3 个 bug

1. **单线程做不到实时**（最重要）。`recv()` 是实时节拍的，拉 20ms 数据就要等 20ms；
   再串 4–6ms 的 DSP 一轮就是 25ms > 20ms，天生落后 25%。
   > 实测：单线程 30 秒 **781 次 overflow** → 加生产者线程 **0 次**
2. **TDD 盲同步用错方法**。阈值找上升沿在 ON 段跨越折叠边界时会分裂成两段而失效
   （实测真实 phase=7000 被误判成 10）。改成**环形滑窗能量最大化**，6 个相位全部零误差。
3. **对比度指标测的是噪声方差不是结构**。`(max-min)/max` 在纯噪声下就能到 0.76，
   会把「没开 TX」误判成锁定。改成**最佳窗内 vs 窗外平均功率之比**：
   有 TDD=0.999 / 纯噪声=0.010，阈值 0.30，~100 倍余量。

### 顺带发现

`get_max_num_samps()` 只有 2040，但**传 200,000 样本的缓冲进去一次 recv 就全返回**，
省掉约 98 次 Python 调用 + 一次整块拷贝。
另：多通道流不能用 `stream_now=True`（报 "fail to time align"），必须给 `time_spec`。

## 六、阶段 2：有人/无人判决（18:45–19:00 + 门限标定）

链路：`功率监控(EMA)` → `CA-CFAR(沿多普勒轴，cumsum 做到 O(N))` → `M-of-N 去抖+迟滞` → 布尔。
全部 O(1) 内存。去抖用**整数位寄存器**（`bit_count()`），真常数内存，没有数组。
判决**只在状态翻转时外发**，不是每帧都发。

### 真机结果（10 MHz，40 秒）

```
2000 步 / 40 秒 = 精确 50 步/秒
p50 5.51ms   p99 8.00ms   预算 20ms   余量 3×
overflow = 0   RSS 60MB 无泄漏
功率监控 ch0 −61.2dBFS / ch1 −61.5dBFS（纯接收机噪声，符合没接 TX）
判决：无人 ✓
```

阶段 2 相比阶段 1 只增加约 **1.5 ms**。

### 检测性能（合成数据，目标 −20dB 弱动目标）

| 场景 | 判决 | 帧命中率 |
|---|---|---|
| 完全静止（巨大 DC） | 无人 ✓ | 0% |
| 纯噪声 | 无人 ✓ | 0% |
| 走路 280Hz / 慢动 60Hz / 退行 −350Hz | **有人 ✓** | **96.3%** |

多普勒峰值精确到 1 个 bin（+281.2 / +58.6 / −351.6 Hz）。

### 修掉的 3 个 bug

1. **CFAR 必须在线性功率上做，不能在 dB 上**——dB 上求均值等于线性上的**几何平均**，
   不是 CFAR 要的算术平均。把 `process()` 改成返回线性 `|S|²`。
2. **DC 保护带 6 Hz 挡不住**。Blackman 主瓣宽度 = `6·fs_out/n_ring` = **30 Hz**，
   DC 铺满 ±15 Hz。改成 20 Hz。
3. **DC 的 EMA 必须热启动**。`alpha=0.01` 时间常数 100 步 = **2 秒**，
   而 ring 只要 0.2 秒就报 ready——中间 1.8 秒的残余 DC 制造大量虚警
   （静止场景帧命中率 12/31）。第一帧直接设成实测均值。

### 门限标定

初版 `pfa=1e-3 + 2bins` 在真机纯噪声下 **40 秒翻转 9 次**（虚警太多）。
扫参数后收紧到 **`pfa=1e-4 + 3bins`**：虚警清零（真机只剩 1 次，是初始播报），
弱目标检出率仍 96.3%。虚警比漏报更坏，所以默认取保守值。

## 七、答疑（~19:00–20:10）

- **「超预算」是什么意思**：处理慢于数据到达 → 积压无限增长 → UHD 缓冲溢出丢样本
- **能不能用 USRP 的 FPGA 加速**：有 Spartan-6，但四个障碍全占（见第四节）
- **能不能不转 float 直接乘**：**能**。int16 直接 einsum + **int64 累加** = 0.78ms，
  和 float 路径（0.72ms）基本打平，且精确无舍入。
  ⚠️ 必须 int64——int32 会溢出且不报错（5000 个乘积每个最大 32767²≈1.07e9）
- **matplotlib blitting 是什么**：只重画变化的部分。实测朴素重绘 26.7ms（超预算 134%）→
  blitting 1.75ms（15× 加速）→ 但 ASCII 瀑布只要 0.025ms，还是快 69 倍
- **瀑布图怎么读**：每行一帧、时间向下流；中间那道 `@` 是 DC（0 Hz），一直都在

# 2026-08-16（周日）会话记录：CFAR 判据结构性重做 + 从根上解决链路强弱变化

延续上面「下次接手」第 1/2 条——CFAR 一直卡在"200Hz 那条线太窄又太稳，老被
CFAR 追到"。这次会话从调参数一路走到重写检测器判据的物理基础，中间有两次
真机复测证伪了自己的方案，最后收敛到一个更干净的架构。全部改动都用真机录制
（不是估算）验证过。

## 一、CFAR 判据结构性 bug：全谱计数 -> 最长连续游程

**发现**：`cfar_min_bins`（数全谱命中 bin 总数）有漏洞——互不相邻的几条窄
线谱能加总凑过阈值（比如 +100Hz 出 2 个 bin、+200Hz 出 3 个 bin，互不相邻，
加起来照样 ≥5），而真人走路的微多普勒是**一整段连续**的（实测 13 个相邻
bin）。改成"找最长连续命中段，段长够不够长"（`longest_run()`，O(n) diff+
where，无额外状态），全链路把 `cfar_min_bins` 重命名成 `cfar_min_run`。

**顺带标定阈值**：真机 `cfar_threshold_db=20` 实测几乎打不着（`bins`/`run`
一直 0）——写了离线 sweep 脚本直接调 `CfarDetector`，发现旧线谱现在只比
CFAR 自己训练出的本底高 中位数3dB/最强13.5dB（8/15 标定时是 10~14dB，物理
场景变了），下调到 `10dB`，配合 `min_run=5`：静止场景 `run>=5` 帧占比在
10dB 时降到 0%，8dB 以下开始有零星虚警——10dB 是"CFAR 从哑火变敏感"和
"游程闸依然零虚警"两者都满足的下限。

## 二、EnergyDetector 基线被"链路变弱"污染 —— 修了又因为同一个坑翻车一次

真人走一圈测试暴露：链路强弱剧烈变化（一次是走动挡断两基站间同步、一次是
TX 自己的行为）时，`EnergyDetector` 的基线环会把骤降期间异常低的能量当成
"真的很安静"学进去，链路一恢复正常就凭空多出 20+dB 余量，判决卡死在"有人"
半分钟起。**第一次修法**（`PowerCeiling`：Rx 功率"健康高水位"，瞬间跟涨/
下降限速，据此判"链路被挡"，被挡帧不喂进基线环）看起来解决了问题——但
**下一次真机测试直接翻车**：这次功率骤降之后**没有恢复**（不是暂时遮挡，
是链路进入了新常态），基线被永久冻结在骤降前的高位，判决从此再也追不上，
present 占比砸到 5%。用户当场指出根子问题：**Rx 功率本身就会因为 TX 自己
的行为涨跌，跟"是不是有人被遮挡"没有必然关系，拿功率去判遮挡这条路本身
就不可靠**，要求整个删掉，换成"相对底噪的能量"思路。

## 三、根治：CAF 在 rt_dsp.py 里按两路各自能量归一化成相关系数 ★ 本次核心改动

**已把 `PowerCeiling`/`PowerMonitor.occluded`/两个 detector 的 `occluded`
参数全部删除**（不是注释掉），`PowerMonitor` 恢复成纯粹的链路健康监控。

**根治办法**：`DopplerEngine.process()` 里 `conj(ch0)·ch1` 逐帧积分后，不再
除以固定的 `SC16_SCALE²×n_int`（相当于假设两路都满量程），改成除以
`sqrt(Σ|ch0|²)·sqrt(Σ|ch1|²)`（本帧两路各自的能量）。`dec` 因此变成**相关
系数**（Cauchy-Schwarz 保证 |dec|<=1），只反映两路"有多同步"，跟两路各自
绝对功率大小（不管什么原因导致的涨跌）完全无关——在最靠近物理量的地方
把共模增益直接除掉，不需要历史、不需要功率监控介入。多花两次 int64
einsum + 一次 float64 sqrt/div，代价可忽略（p99 从 ~2ms 涨到 ~3ms，预算
20ms，仍有 7x 余量）。

**数学验证**：用 `DopplerEngine` 直接跑合成数据，同一个 120Hz 目标，把两路
信号幅度骤降到 1/30（≈-59dB 功率，比真机两次实测的骤降都更极端），归一化
后非DC均值功率**变化量 0.00dB**，峰值频率/幅度完全不变——旧算法这个量级
下应该有 ~40dB 跳变。

## 四、归一化的副作用：TX 杂散线在相关系数尺度下变得异常强 -> 加陷波口

归一化上线后立刻在下一次真机测试暴露：2s 挥了下胳膊、人就走了，但
`present` 从 2.5s 一路卡死到 12.5s（100% 占比）。查真实谱发现：±100Hz/
±200Hz 现在比本底高 **32~35dB**，自己就占 6~8 个连续 bin（不是几条线凑数，
单独一条线自己就够宽了），±300/400Hz +22~25dB(5~6bin)，±50/150Hz
+9~10dB(3~4bin)。

**物理解释**（值得记住）：TX 自己那套周期性调制是发射信号自带的，不依赖
多径，两路天线几乎完全同步收到；换算成相关系数后它逼近 ρ≈1（贴理论上限）。
人体反射是弱相干散射（两天线角度/路径不同，相关性天然低）。**解决了增益
问题，副作用是把这条本来就"很同步"的杂散线相对衬得比人强得多**——宽度
判据（run-length）单靠自己已经防不住振幅这么强的线，`EnergyDetector` 的
宽带平均功率也被直接抬高，两个判据都要挡。

**修法**：`rt_config.py` 新增 `notch_freqs_hz=(50,100,150,200,300,400)` +
`notch_guard_hz=20`（250/350/450 目前干净，先留着能用），新增
`valid_mask(freqs, cfg)`，CFAR 和 EnergyDetector **共用同一个陷波掩码**
（跟 DC guard 同一个机制，只是多开了几个口）。`debug/replay.py` 的
`PresenceDetector` 构造也同步改用 `valid_mask()`。

**真机验证**：同一份"挥手后人消失"的录制，2.5-12s 那段 present 占比从
**100% 降到 16%**，翻转时刻从卡死到 12.48s 才退出，变成 **4.00s 就退出**
（4s 比实际 2-3s 稍晚，是 0.6s 去抖窗的正常延迟）。用户确认满意。
