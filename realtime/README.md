# realtime — 实时多普勒 + 有无检测

不落盘、不存历史。**阶段 1（多普勒）和阶段 2（有人/无人判决）都已完成并真机验证。**
设计依据见上层 [REALTIME_PROMPT.md](../REALTIME_PROMPT.md)。

## 跑

**必须用 `/usr/bin/python3`**（默认 `python3` 是 miniconda，没有 uhd）：

```bash
cd RealtimeISAC/realtime
/usr/bin/python3 rt_main.py --duration 30              # 单行峰值输出
/usr/bin/python3 rt_main.py --duration 30 --waterfall  # ASCII 瀑布（"视频"）
/usr/bin/python3 rt_main.py --dry-run --duration 10    # 不碰硬件，合成数据自检
/usr/bin/python3 rt_main.py --fs 30 --duration 20      # 换采样率
/usr/bin/python3 rt_main.py --duration 40 --publish    # 判决以 JSON 外发
```

### 接你自己的 IP 推送

`rt_publish.py` 已经把非阻塞外发写好了，只要把你的推送函数传进去：

```python
from rt_publish import Publisher
pub = Publisher(sink=my_push_to_ip).start()
# 状态翻转时自动发 {"present": true, "doppler_hz": 281.2, "bins": 5, "t": ...}
```

**唯一硬性要求：sink 不能阻塞。** 一次卡住的 socket 写就能吃掉整个 20ms 预算，
连锁导致采集溢出。所以 Publisher 用独立线程 + 队列满丢最旧的，
sink 里抛异常也只会被计数，不会影响 DSP。

判决**只在状态翻转时外发**，不是每帧都发——下游要的是事件不是流。

## 实测结果（2026-08-14，B210 serial=32392D3，真机）

| fs | 步数/时长 | p50 | p99 | 余量 | overflow | RSS |
|---|---|---|---|---|---|---|
| **10 MHz** | 3000 / 60s | **4.07 ms** | **5.86 ms** | **3×** | **0** | 60 MB（平） |
| 10 MHz | 1500 / 30s | 4.18 ms | 6.08 ms | 3× | 0 | 60 MB |
| 30 MHz | 1214 / 25s | 9.24 ms | 14.57 ms | 1× | **51** ⚠️ | 92 MB |

- 10 MHz 下 **3000 步 / 60 秒 = 精确 50 步/秒**，完全跟上实时。
- **无内存泄漏**：30s 涨 27.8 MB，60s 涨 27.3 MB，完全一致（都是启动期的一次性分配）。
- 30 MHz = 240 MB/s，接近 B210 USB 3.0 实用上限，余量仅 1×，**不推荐**。

以上均为**自由运行模式**（没接 TX，测不到 TDD 结构，`n_integrate` 取满周期）。
真接上 TX 后 TDD 锁定，每帧只积分 ON 段，计算量减半，p99 应降到 ~3 ms。

## 三个踩过的坑（别改回去）

### 1. 必须用生产者线程，单线程做不到实时

`recv()` 是**实时节拍**的：拉 20 ms 数据就要等 20 ms（实测吞吐恰好 80 MB/s @10MHz）。
单线程里再串 4–6 ms 的 DSP，一轮 25 ms > 20 ms 预算，**天生落后 25%**。

> 实测：单线程 30 秒 → **781 次 overflow**；加生产者线程 → **0 次**。

### 2. `recv()` 会填满大缓冲

`get_max_num_samps()` 只有 2040，但传 200,000 样本的缓冲进去，**一次 recv 就返回 200,000**
（UHD 内部连收多个包）。所以直接 recv 进整个 step 缓冲，省掉 ~98 次 Python 调用和一次整块拷贝。

另：多通道流 **不能** 用 `stream_now=True`，UHD 会报
`Invalid recv stream command - stream now on multiple channels will fail to time align`，
必须给 `time_spec`。

### 3. TDD 盲同步：滑窗能量最大化，不是阈值找上升沿

阈值找上沿在 ON 段跨越折叠边界时会分裂成两段而失效（实测真实 phase=7000 被误判成 10）。
改成**环形滑窗能量最大化**——直接回答"从哪开始积分能收到最多能量"，天然 wrap-safe。

对比度指标也不能用折叠包络的极值张开 `(max-min)/max`：那测的是噪声方差不是结构，
纯噪声下就能到 0.76，会把"没开 TX"误判成锁定。改成**最佳窗内 vs 窗外的平均功率之比**。

| 场景 | 旧指标 | 新指标 |
|---|---|---|
| 有 TDD 结构 | 1.00 | **0.999** |
| 纯噪声（没开 TX） | 0.76 ❌ | **0.010** ✅ |

阈值 0.30 落在中间，~100 倍余量。

## 阶段 2：检测（已完成）

链路：`功率监控` → `CA-CFAR(沿多普勒轴)` → `M-of-N 去抖 + 迟滞` → 布尔判决。
全部 O(1) 内存，不存任何历史谱。

### 合成数据标定（每档 200 帧 = 4s）

| pfa | min_bins | enter | 静止(巨大DC) | 纯噪声 | 走路280Hz | 慢动60Hz |
|---|---|---|---|---|---|---|
| 1e-3 | 2 | 8 | 0次 / 0.0% | **2次 / 6.8%** | 96.3% | 96.3% |
| **1e-4** | **3** | **8** | **0次 / 0.0%** | **0次 / 0.0%** | **96.3%** | **96.3%** |
| 1e-5 | 3 | 10 | 0次 / 0.0% | 0次 / 0.0% | 95.3% | 95.3% |

目标是 **−20 dB 的弱动目标**（叠在静止杂波上）。检出率里那 3.7% 的缺口是
ring 灌注期，不是漏检。**虚警（误报有人）比漏报更坏**，所以默认取 `1e-4 + 3bins`。

真机复测（10 MHz，40 秒，没接 TX 所以应判"无人"）：
`1e-3+2bins` → **9 次状态翻转**；收紧到 `1e-4+3bins` → **1 次**（那 1 次是初始播报）。

### 两个非显然的设计点

**1. CFAR 必须在线性功率上做，不能在 dB 上。**
dB 上的均值等于线性上的**几何**平均，不是 CFAR 要的算术平均。
所以 `engine.process()` 返回线性 `|S|²`，显示时才用 `to_db()` 转（只有 256 点）。

**2. DC 保护带必须 ≥ 15 Hz，早先设的 6 Hz 挡不住。**
Blackman 主瓣宽度 = `6*fs_out/n_ring` = 6×1000/200 = **30 Hz**，
即 DC 能量铺满 ±15 Hz。默认取 20 Hz 留余量。
代价：看不到 v < 0.12 m/s（25 GHz 下）的极慢运动。

**3. DC 的 EMA 必须热启动。**
`alpha=0.01` 的时间常数是 100 步 = **2 秒**，而 ring 只要 10 步（0.2 s）就报 ready。
中间那 1.8 秒的残余 DC 会制造大量虚警（实测静止场景帧命中率 12/31）。
第一帧直接把 DC 设成实测均值即可消除。

## ⚠️ 接上真实系统后必须重做的事

1. **重新标定 CFAR 门限。** 现在的 `pfa=1e-4 / min_bins=3` 是在**纯接收机噪声**下
   标的，不是真实工作条件。接上 TX 后静止杂波的统计完全不同，必须拿"确定没人"
   和"确定有人"两段真实数据重新扫参数。
2. **验证 TDD 锁定。** 现在一直是自由运行模式，`rt_sync` 的锁定路径从未在真信号上跑过。
   看输出里 `TDD锁定 phase=... 对比度=0.99` 是否出现。
3. **确认门控后的时序余量。** 锁定后每帧只积分 ON 段，计算量减半，p99 应降到 ~3 ms。
